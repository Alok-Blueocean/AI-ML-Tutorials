# Scenario-Based Q&A — Model Evaluation and Overfitting

**Situation**: Your churn-prediction model reports 98% accuracy in the review meeting, but the business team says it's useless — they can't find the customers who are actually about to churn.
**Answer**: Churn is almost always a rare-class problem (maybe 2-5% churn per month), so a model predicting "will not churn" for everyone already scores ~95-98% accuracy while catching zero real churners — the accuracy paradox. I'd immediately pull the confusion matrix and report precision/recall/F1 or PR-AUC instead of accuracy, check whether the model even learned a useful decision boundary versus just exploiting class imbalance, and tune the classification threshold against the actual business cost of a missed churner (lost revenue) vs. a false alarm (wasted retention offer) rather than the default 0.5 cutoff.

**Situation (small tabular dataset overfitting)**: You have only 800 labeled rows and 60 features for a medical diagnosis classifier. A gradient-boosted model gets 99% training accuracy but only 68% on a held-out test set.
**Answer**: This is a textbook high-variance regime — far too many features relative to rows, so the model memorizes idiosyncrasies of the 800 rows. I'd work the overfitting toolkit in order of expected impact for this situation: (1) aggressively reduce model complexity — shallow trees, fewer estimators, higher `min_child_weight`/`min_samples_leaf`; (2) add L1/L2-style regularization (`reg_alpha`/`reg_lambda` in XGBoost, or switch to a regularized linear/logistic model as a baseline); (3) do feature selection to cut the 60 features down to the ones with real signal (e.g., via permutation importance or Lasso), since with n=800 many of those 60 are likely noise; (4) use k-fold (or repeated k-fold / nested CV, given how small the dataset is) rather than a single train/test split, since a single split's test score is itself noisy at this sample size; (5) actively look for more labeled data or a related public dataset to pretrain/transfer from, since more data is the single highest-leverage fix here if it's obtainable at all.

**Situation (deep learning overfitting)**: You're training a CNN on 5,000 medical images. Training accuracy climbs to 99.8% while validation accuracy plateaus around 75% after epoch 10, and validation loss starts rising after that.
**Answer**: Classic deep-learning overfitting, visible directly in the diverging train/val loss curves — the fix set is different in character from the tabular case because you have more levers tied to the training process itself. I'd apply, roughly in this order: (1) early stopping at the epoch where validation loss is minimized, not where training ends; (2) data augmentation (rotations, crops, flips, color jitter) since 5,000 images is small for a CNN and augmentation is nearly free signal; (3) dropout in the fully-connected head and/or weight decay (L2) on the conv/FC layers; (4) transfer learning — fine-tune a pretrained backbone (e.g., ImageNet-pretrained ResNet/EfficientNet) instead of training from scratch, since the pretrained features reduce the effective capacity being fit to your small dataset; (5) reduce model capacity (fewer layers/channels) only if the above don't close the gap, since an overly small model risks trading variance for bias.

**Situation (high-cardinality categorical feature overfitting)**: You add a `merchant_id` feature (50,000 unique values) to a fraud model using simple mean target encoding. Training AUC jumps to 0.99, but production AUC on new merchants a month later is only 0.71.
**Answer**: Naive target encoding computed on the full training set leaks the label into the feature — merchants with very few transactions get an encoded value nearly identical to their own (often single) target outcome, so the model effectively memorizes training labels through that one column, and it collapses on unseen or low-frequency merchants at inference. I'd fix this with out-of-fold / K-fold target encoding (compute each row's encoding using target statistics from the *other* folds only), add smoothing that blends a merchant's mean toward the global mean when its sample count is low (Bayesian/empirical-Bayes smoothing), and add a fallback bucket ("unknown"/"other") for merchants with too few transactions or that are unseen at inference. I'd also validate using a merchant-based (grouped) train/test split rather than a random row split, since a random split still lets the same merchant appear in both train and test and hides this exact failure mode.

**Situation**: A demand-forecasting model shows a great CV R² of 0.91 using standard 5-fold cross-validation, but forecasts for next month are consistently far off once deployed.
**Answer**: This smells like a time-series CV mistake — standard shuffled k-fold lets the model train on data from *after* the point it's validating on, which is impossible in a real forecasting deployment and inflates the CV score. I'd re-validate using walk-forward / rolling-origin CV (train on the past, validate strictly on the following period, roll forward) to get an honest performance estimate, and check for other leakage sources too, such as features computed using information not actually available at prediction time (e.g., an aggregate that includes future values).

**Situation**: Your team ran a large grid search with 5-fold CV to pick hyperparameters and reported the best CV fold score as the model's expected production performance. A senior engineer says this number is likely too optimistic. Why, and what would you do differently?
**Answer**: They're right — using the same CV folds both to select the best hyperparameters and to report performance introduces selection bias; you're implicitly picking the configuration that got lucky on those specific folds, so the reported score overstates true generalization. I'd use nested cross-validation: an inner CV loop tunes hyperparameters within each outer training fold, and the outer loop's held-out folds (never used for tuning) give an unbiased estimate of generalization performance, at the cost of more compute.

**Situation**: A model trained on last year's customer data performs well in offline evaluation but degrades gradually in production over several months, with no code or data pipeline changes.
**Answer**: This points to a bias-variance issue morphing into a **distribution shift** problem over time rather than classic overfitting at training time — the world is changing (customer behavior, market conditions) faster than the model is being refreshed. I'd set up production monitoring for feature distribution drift and prediction-vs-actual drift, establish a retraining cadence (or trigger-based retraining when drift exceeds a threshold), and make sure the retraining pipeline uses walk-forward validation so each retrain is judged the way it will actually be used.

**Situation**: Your manager asks you to "just add more layers" to a struggling deep learning model because "bigger models are always better."
**Answer**: More capacity reduces bias but increases variance — it only helps if the current bottleneck is underfitting (both train and val error are high and close together) rather than overfitting (train error low, val error high and diverging). I'd first check the learning curves and train/val gap to diagnose which regime we're actually in; if it's underfitting, more capacity (or better features/architecture) is the right call, but if it's overfitting, adding layers will make things worse unless paired with proportionally more data, stronger regularization, or dropout — I'd present the diagnosis before agreeing to the "just add more layers" plan.
