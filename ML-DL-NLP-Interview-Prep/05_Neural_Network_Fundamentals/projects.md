# Projects — Neural Network Fundamentals

## Small: Backprop From Scratch on Tabular Fraud Data
Build a 2-3 layer MLP entirely in NumPy (no autograd frameworks) — forward pass, manual backprop, and an Adam or SGD+momentum update rule you also implement by hand. Train it on the Kaggle "Credit Card Fraud Detection" dataset (creditcard.csv, ~285k transactions, 30 anonymized PCA features, 0.17% fraud rate). Report precision/recall (not just accuracy, given the imbalance). This proves you understand what `loss.backward()` actually does rather than treating it as a black box — a very common interview follow-up is "implement backprop without autograd."

## Medium: Initialization and Regularization Ablation Study
Using PyTorch on the UCI "Adult"/Census Income dataset or Fashion-MNIST, train the same architecture 6+ times varying one factor at a time: Xavier vs. He init, with/without dropout, with/without batch norm, with/without weight decay, SGD vs. Adam. Log train/val loss curves for every run (a simple `matplotlib` grid or a TensorBoard dashboard) and write a short comparison of which combination generalizes best and why. This proves you can reason empirically about the regularization and optimization choices interviewers probe, not just recite definitions.

## Medium-Large: "Explain the Gradient" Diagnostic Tool
Build a small diagnostic utility (CLI or notebook) that, given a PyTorch model and a batch, reports per-layer gradient norms and activation statistics (mean/std/fraction-saturated) after a forward+backward pass — essentially a mini vanishing/exploding-gradient detector. Validate it by deliberately constructing a 15-layer sigmoid MLP (which should show vanishing gradients) versus the same depth with ReLU + He init + batch norm (which should not). This is close to real production debugging work and demonstrates you can diagnose training pathologies rather than just avoid them by convention.

## Large: Architecture Search for a Constrained Deployment Target
Given a fixed inference latency/parameter budget (e.g., <1M parameters, <10ms CPU inference), design and empirically compare 4-5 candidate MLP architectures (varying depth, width, activation) on a real tabular dataset (e.g., UCI "Bank Marketing" or a Kaggle tabular competition dataset), tracking accuracy vs. parameter count vs. inference latency. Present the Pareto frontier and justify a final recommended architecture. This mirrors the real interview scenario "design a network under a resource constraint" and proves you can trade off capacity against deployment cost, not just chase accuracy.

## Large: Four Problems, Four Justified Architectures (Design-Decision Portfolio)
Build and justify four small neural nets for four different problem types, using a real or realistic dataset per scenario:
1. **Imbalanced tabular fraud** — Kaggle "Credit Card Fraud Detection" (creditcard.csv, ~285k transactions, 0.17% fraud). Output layer, loss (plain BCE vs. class-weighted vs. focal), and regularization must all be justified against the imbalance.
2. **Small multi-class image set** — a subset of CIFAR-10/Fashion-MNIST or a small Kaggle image dataset restricted to ~2-3k images across 10 classes, to force the transfer-learning-vs-scratch decision and a Flatten-vs-GlobalAveragePooling justification before the classifier head.
3. **Multi-label text tagging** — Kaggle "Multi-Label Image Classification Dataset" (or a text equivalent such as a StackOverflow/arXiv multi-tag dataset) where each item can carry several simultaneous labels, forcing the sigmoid-per-label + binary cross-entropy design instead of softmax.
4. **Skewed-target regression** — a Kaggle insurance-claims or ride-fare dataset with a heavy-tailed target, forcing a choice among MSE, MAE, Huber, and a log-transformed target.

For each of the four, write a short (half-page) justification covering: chosen output layer + activation, loss function, one regularization/architecture choice, and the learning curves (train vs. val loss/metric) that led to the final choice — including at least one *rejected* alternative and why the curve ruled it out (e.g. "plain BCE was rejected because precision on the minority class stayed near 0 despite falling loss"). This project is designed to be the single strongest interview artifact from this module: it demonstrates the full capacity-then-regularize loop and the output-layer/loss/activation decision table applied to genuinely different problem shapes, not just one dataset tuned four ways.

## Medium: Regularization Placement Ablation on a Single Architecture
Take one moderately deep architecture (e.g. a 6-layer MLP on Fashion-MNIST, or a small CNN) and hold the architecture fixed while only changing *where* Dropout and BatchNorm are placed: (a) Dropout after every Dense layer including the input and pre-output layers (the "wrong" placement described in `tutorial.md`), (b) Dropout only after hidden-layer activations, (c) BatchNorm before activation, (d) BatchNorm after activation, (e) Dropout immediately after BatchNorm vs. before it. Plot train/val curves for each variant and report which placements measurably hurt or help. This is a fast, focused project that turns the "where do I put Dropout/BatchNorm" question from a memorized rule into something empirically verified on your own hardware.
