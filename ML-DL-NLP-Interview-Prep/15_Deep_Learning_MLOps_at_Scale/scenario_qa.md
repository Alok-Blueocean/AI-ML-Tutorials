# Deep Learning MLOps at Scale — Scenario-Based Q&A

**Situation:** Five ML teams share one MLflow model registry, and two teams have both registered a model called `fraud-model`, with a third team's serving code accidentally pointing at the wrong one after a promotion. How do you structure naming and governance to prevent this?

Model answer: Enforce a naming convention at the point of registration, not after the fact — e.g., `<team>-<usecase>-<architecture>` (`payments-fraud-cnn`, `risk-fraud-xgb`), ideally validated by a CI check on the registration call itself so a colliding or non-conforming name simply fails to register. Move promotion off ad-hoc "production" naming and onto aliases scoped to the fully-qualified model name (`models:/payments-fraud-cnn@champion`), so serving code references an unambiguous, team-owned identifier rather than a generic label. Require a second approver to record sign-off (as a registered tag, e.g. `approved_by`, `approval_ticket`) before an alias reassignment, so "who promoted this and why" is queryable, not tribal knowledge. Finally, give each team registry permissions scoped to their own name prefix, so a naming collision becomes a permissions error at write time instead of a production incident discovered later.

**Situation:** A SageMaker real-time endpoint serving a deep learning model shows latency spikes specifically after autoscaling events add new instances, even though steady-state latency is fine. What do you do?

Model answer: This is a classic GPU cold-start problem — a newly launched instance has to download the model artifact, load it into GPU memory, and (if using a multi-model endpoint) warm up before it serves at steady-state latency, and requests routed to that instance during warmup see the spike. First confirm it's cold-start and not something else by correlating the latency spike timestamps with `CloudWatch`'s instance-launch events for the endpoint. Mitigations, roughly in order of effort: increase the minimum instance count so autoscaling adds capacity less frequently and further ahead of demand (trading idle-GPU cost for smoother scaling); tune the autoscaling policy's target metric and cooldown so it scales out earlier, before load fully saturates existing capacity; and if using a multi-model endpoint, pre-warm frequently-needed models rather than relying on lazy load-on-first-request. If the workload is spiky and cost-sensitive rather than latency-critical, asynchronous inference (which tolerates queuing) may be a better fit than a real-time endpoint fighting cold starts.

**Situation:** You need to choose between a SageMaker real-time endpoint, batch transform, and asynchronous inference for three different DL use cases: a fraud-scoring API on live transactions, nightly batch scoring of a customer table, and a slow video-processing model. How do you decide, and what do you pick for each?

Model answer: The decision hinges on latency requirement, payload size, and whether traffic is persistent or bursty — not just "online vs. offline." Fraud scoring on live transactions needs millisecond, request/response latency on a small payload with persistent (if bursty) traffic — that's a real-time endpoint, sized and autoscaled for the transaction rate. Nightly batch scoring of a whole customer table is a large, known-upfront dataset with no latency pressure and no need for an always-on endpoint — batch transform spins up compute, processes the full dataset, and tears down, which is both simpler and cheaper than keeping an endpoint alive for a job that runs once a day. The slow video-processing model has large payloads (video files) and processing times that can run well past what a real-time endpoint's timeout tolerates, but the caller still wants a result back on a reasonable timescale rather than waiting for a full batch cycle — asynchronous inference fits exactly this gap: it queues the request, tolerates payloads up to 1GB and processing up to an hour, and can scale the instance count to zero between requests so a low-traffic, slow model doesn't pay for an idle real-time endpoint 24/7.

**Situation:** You need to serve a large deep learning model (say, a multi-billion-parameter model) and are deciding between a SageMaker-managed endpoint and a self-hosted NVIDIA Triton server on Kubernetes/EKS. What factors decide it?

Model answer: Weigh operational ownership against control and cost at scale. A SageMaker-managed endpoint wins when the team wants autoscaling, deployment guardrails (blue/green with auto-rollback), and IAM-based access control without building or operating that infrastructure — the right default when the team's leverage is best spent on the model, not the serving platform. A self-hosted Triton deployment on EKS wins when: the org already runs Kubernetes infrastructure and has the platform engineering capacity to operate it; cost at scale matters enough that avoiding SageMaker's managed premium is worth the operational burden (especially once you're running dozens of large, expensive GPU instances continuously); you need serving topology SageMaker doesn't natively support (e.g., a custom multi-model ensemble pipeline, exotic multi-GPU sharding, or tight integration with existing in-cluster services); or you're explicitly trying to avoid deeper AWS lock-in. In practice, many large orgs land on a hybrid: SageMaker for teams and workloads where speed-to-production matters most, self-hosted Triton/KServe for the highest-cost or most custom serving workloads where the savings and control justify the operational investment.

**Situation:** A new model version was promoted to production and is now underperforming — user complaints are up and a downstream business metric has dropped. How do you roll back safely?

Model answer: Roll back at both the registry level and the traffic level, and don't wait for a root-cause diagnosis before reverting — stop the bleeding first, investigate after. At the registry level, reassign the promotion pointer back to the previous known-good version immediately: in MLflow, reassign the `@champion` alias back to the prior model version; in the SageMaker Model Registry, mark the bad version's approval status as rejected/revoked and ensure serving references the last approved version. At the traffic level, if the bad version is live behind a SageMaker endpoint using deployment guardrails (blue/green with canary or linear traffic shifting), trigger the built-in auto-rollback — or if it wasn't caught by a CloudWatch alarm automatically, manually shift traffic back to the still-running blue fleet, which is exactly why you keep the previous fleet warm during a shift rather than terminating it immediately. Afterward, do a blameless review: what pre-promotion check (a fixed eval-set threshold, a canary stage, a business-metric proxy) should have caught this before full rollout, and close that specific gap rather than adding generic process.

**Situation:** GPU spend for deep learning endpoints is spiraling as more teams deploy models, and finance is asking for a plan. What levers do you pull?

Model answer: Attack it in order of effort-to-savings ratio, but pull all of them for a real cost problem. First, get visibility: tag every endpoint and training job by team/project so GPU spend is attributable, not just an aggregate line item — you can't fix what you can't see per-team. Then, consolidate low-traffic workloads onto shared multi-model endpoints instead of dedicated always-on GPU endpoints per team — this is usually the single biggest lever, since most endpoint sprawl is many mostly-idle GPUs. For bursty or non-latency-critical workloads, move to asynchronous inference with scale-to-zero rather than a persistent real-time endpoint. Right-size instance types against actual GPU utilization metrics (a model comfortably fitting on a smaller GPU doesn't need the biggest instance in the fleet). Turn on managed spot training for anything that isn't latency-sensitive at train time — up to ~90% training cost savings, with checkpointing to tolerate interruption. And apply serving-side optimization (dynamic batching, TensorRT/ONNX Runtime compilation) before assuming you need more or bigger instances — inefficient GPU utilization is often the real problem instance rightsizing alone won't fix.

**Situation:** You're training a transformer model that doesn't fit in memory on a single GPU. Do you reach for SageMaker's distributed training libraries, or plain PyTorch DDP/Horovod/DeepSpeed, and how do you decide?

Model answer: First clarify which scaling problem you actually have — "doesn't fit on one GPU" is a model-parallelism problem (the model itself needs to be sharded across devices), which plain data-parallel tools like PyTorch DDP or Horovod don't solve at all, since those assume the full model fits on each GPU. That points toward SageMaker's model-parallel library (SMP) or an equivalent like DeepSpeed ZeRO/PyTorch FSDP. The decision between SageMaker's managed libraries and a self-managed DeepSpeed/FSDP setup then comes down to: how AWS-committed the team already is (SMP only runs inside SageMaker training jobs, so it's a deeper lock-in than a framework-native solution that runs anywhere); whether the team wants AWS-network-optimized collective communication out of the box versus needing to tune that themselves; and whether the existing team expertise is with SageMaker's SDK or with the open-source distributed training ecosystem, since both solve the same underlying sharding problem and the switching cost of learning either is real. For a pure data-parallelism need (model fits on one GPU, training is just slow), the calculus is similar but lower-stakes: SageMaker's SMDDP library vs. plain PyTorch DDP, where SMDDP mainly buys AWS-tuned AllReduce/AllGather performance at the cost of being AWS-specific.

**Situation:** A production incident traces back to a training run using a slightly different container image or dependency version than what's recorded in the model registry — the registered model can't actually be reproduced. How do you prevent this at scale?

Model answer: The root cause is almost always that only hyperparameters and code commit got versioned, while the exact runtime environment (base container image digest, pinned dependency versions) didn't travel with the registered model as one atomic unit. Fix it by logging the container image digest (not just a mutable tag like `:latest`) as a run parameter or model tag at training time, and make CI reject a registration that doesn't include it — decoupling "what code ran" from "in what environment it ran" is exactly what lets these drift apart. Pin dependencies explicitly (a lockfile, not a loose requirements range) inside the training container build, and rebuild/re-tag that container deliberately rather than letting a base image update silently roll forward. At scale, put this behind a template: every team's SageMaker Pipeline or training job is generated from a shared pipeline definition that always logs image digest + dependency lockfile hash + code commit + data version together as one reproducibility record attached to the registered model, so no team can register a model without that record existing.

**Situation:** A DL platform team is evaluating whether to adopt TorchServe as the standard serving layer for a new project, based on older documentation that recommends it as the default PyTorch serving solution. What would you tell them?

Model answer: Check current maintenance status before standardizing on it — as of this session's check, the `pytorch/serve` GitHub repository is archived (no longer actively maintained as of August 2025), meaning no further bug fixes or security patches are planned even though existing releases remain usable. It's still functionally present in places (e.g., wired in as SageMaker's default PyTorch inference container as of this check), so it isn't broken today, but building a new serving standard around an unmaintained project is a real long-term risk, especially for anything security-sensitive or expected to run for years. For a new project, recommend NVIDIA Triton Inference Server (actively maintained, multi-framework, GPU-efficient dynamic batching) or TensorFlow Serving if the models are TensorFlow-only, and reserve TorchServe only for short-lived or low-stakes workloads where its current state is an acceptable, explicitly-acknowledged risk.

**Situation:** Leadership wants deep learning inference cost to go down without a corresponding drop in the number of models teams can ship. Where do you look first, specifically for the DL-model-serving layer (as distinct from general infra cost)?

Model answer: Look at GPU utilization efficiency before touching headcount of models or instances. Check whether requests are being batched at all — a naive one-request-at-a-time server on a GPU can leave most of its throughput unused, and adding dynamic batching (via Triton or an equivalent) is frequently a multiple-x throughput improvement on the same hardware with no accuracy cost. Next, check whether models are compiled/quantized for inference (TensorRT engine, ONNX Runtime with an appropriate execution provider) — this is usually the second-biggest lever and, again, doesn't reduce the number of models you can ship, just the cost of serving each one. Only after those two are addressed does consolidating low-traffic models onto shared multi-model endpoints and right-sizing instance types become the next round of savings — and note explicitly to leadership that none of these levers require shipping fewer models; they require serving each one more efficiently, which is the actual ask.
