# Tool / Function Calling and MCP — Scenario-Based Q&A

**Situation:** Your production agent starts throwing errors because the model occasionally emits a tool call missing a required argument, or with a value of the wrong type (a string where an integer was expected). This started happening more often after you added a 30th tool to the agent's toolset. What would you do and why?

Model answer: First separate the two contributing causes. The immediate fix is defensive: validate every tool call's arguments against the schema before execution (Pydantic or equivalent) and return a specific, actionable error as a tool_result with is_error set, rather than letting a malformed call crash the pipeline — most models will self-correct within 2-3 turns given a clear validation message. If the provider supports strict/schema-constrained tool calling, turn it on so malformed calls are prevented at generation time instead of caught after the fact. Second, treat the timing correlation with the 30th tool as a real signal, not a coincidence: tool-selection and argument accuracy degrade as the tool list grows, so audit whether the new tools have ambiguous names/descriptions or overlapping purpose with existing tools, and consider grouping tools into named toolsets or adding a routing step so the model isn't choosing among 30 options on every turn.

**Situation:** You need to decide whether to expose your company's product-catalog database to AI agents as an MCP server, or just write a bespoke tool function inside your one existing chatbot. Leadership is asking why you'd take on the extra complexity of standing up a server and a protocol. What would you do and why?

Model answer: Frame it around reuse, not novelty. If the product catalog will only ever be queried by this one chatbot, in this one codebase, a bespoke in-process tool is genuinely simpler — no separate process to run, deploy, and secure, no protocol overhead. The case for MCP is that the same catalog is very likely to be needed again: a support-ticket assistant, an internal BI chat tool, maybe eventually a partner-facing agent, all wanting the same data. Building one MCP server once, with one auth and permission model, means each new consumer connects as a generic MCP client instead of getting its own bespoke integration with its own bugs and its own stale copy of "how the catalog schema works." Recommend checking with product/other teams now whether a second consumer is realistically coming within, say, two quarters — if yes, build the MCP server now while there's only one consumer to migrate; if genuinely no other consumer will ever exist, the bespoke tool is the right call and MCP would be premature abstraction.

**Situation:** Your agent calls three independent tools in parallel to answer "what's the weather, traffic, and event schedule for downtown this weekend?" Occasionally the final answer contains stale or clearly wrong information from one of the three, even though each tool individually returns correct data when tested alone. What would you do and why?

Model answer: This is very unlikely to be a race condition on data itself, since the three lookups are independent reads with no shared state to corrupt — but check the result-matching logic first anyway: verify every tool_result is being matched to its tool_use_id correctly and that results aren't being appended out of order relative to their calls, since a bug there would silently attach the wrong observation to the wrong call summary. Next check for a timeout-and-partial-result bug: if one of the three calls is slow and your code has a timeout that returns a stale cached value instead of failing loudly, that would explain intermittent staleness. Add explicit timestamps to each tool result and log the full parallel batch (which calls fired, when each returned, what was passed to the model) so the next occurrence is diagnosable from the trace instead of guessed at. If the tools do share any state (e.g., a shared HTTP session or connection pool with reused buffers), audit that for a genuine concurrency bug — that's the one class of "parallel tool call" issue that's a real race condition rather than a plumbing bug.

**Situation:** A stakeholder asks: "our agent has 60 tools now and accuracy on tool selection has visibly dropped — what do we do?" What would you do and why?

Model answer: Tool-selection accuracy degrading as the tool list grows is an expected, well-documented failure mode, not a mysterious regression — treat it as a design problem, not a model problem. Concretely: audit tool names and descriptions for ambiguity and overlap (two tools that sound like they do the same thing will be confused for each other regardless of model quality); group tools into named toolsets scoped to task type and load only the relevant subset per request instead of exposing all 60 on every call; consider a lightweight routing/classification step ahead of the main reasoning call to narrow candidates first. Also apply the tool-design guidance directly: consolidate related fine-grained tools into fewer, more capable ones with an action parameter (e.g., one `manage_ticket` tool instead of `create_ticket`/`update_ticket`/`close_ticket`) to shrink the selection surface without losing capability. Measure the fix against a tool-selection accuracy eval set before and after, since "fewer, clearer tools" is a hypothesis that needs verifying, not an assumption.

**Situation:** You're building an agent that connects to a third-party MCP server you don't control (a partner's CRM integration). During a security review, someone asks how you know that server's tools won't be used to exfiltrate data or manipulate the model. What would you do and why?

Model answer: Point to MCP's own stated security posture rather than assuming trust by default: the spec is explicit that tool descriptions and annotations should be treated as untrusted unless they come from a known-trusted server, because a malicious or compromised server can write a tool description crafted to manipulate the model (tool poisoning), and tool results returned from that server should likewise be treated as untrusted data, not instructions, for the same indirect-prompt-injection reason that applies to any external content fed into an LLM. Concretely: require explicit user/operator consent before connecting to any new remote MCP server, review the server's exposed tool list and descriptions before enabling it in production, run tool results through the same content-handling discipline you'd apply to untrusted web content, and log every call made to that server for audit. If the partner's server needs write access to anything sensitive, gate those specific tools behind human confirmation regardless of how much you otherwise trust the partner.

**Situation:** Your team is debating whether to use Anthropic's remote MCP connector (calling a hosted MCP server directly from the Messages API via the `mcp_servers` parameter) versus running your own MCP client in your backend that talks to the same server. What factors would you weigh, and what would you recommend?

Model answer: The remote connector is simpler when you want Claude to talk to a public or already-hosted remote MCP server directly and don't need custom control over the tool-execution step — fewer moving parts, no client code to maintain, but also less control: you can't intercept, validate, or rate-limit individual tool calls before they hit the third-party server, and the server must be reachable over the public internet from Anthropic's infrastructure, which rules out anything behind a private VPN or corporate firewall. Running your own MCP client gives you a control point to add logging, argument validation, rate limiting, and human-approval gates before a call reaches the server, and works for internal servers that are intentionally not internet-reachable. Recommend the connector for genuinely public, low-risk, well-trusted third-party servers, and a self-hosted client for anything internal, sensitive, or where you need an audit/approval layer in the middle.

**Situation:** An agent occasionally issues the same non-idempotent tool call twice — e.g., a `send_invoice_reminder` email tool fires twice for the same invoice — because the tool actually succeeded but the HTTP response timed out, and your retry logic treated the timeout as a failure and retried. What would you do and why?

Model answer: This is a classic at-least-once-delivery problem, not a tool-calling-specific bug, and the fix is standard: make the underlying operation idempotent by having the caller generate and pass an idempotency key (e.g., a hash of invoice ID + reminder type + date) that the receiving service uses to deduplicate, so a retried call with the same key is a safe no-op rather than a second email. Separately, tighten what counts as "retryable": a response timeout where you genuinely don't know if the server-side action completed should, where possible, be resolved with a status check (does the invoice show a reminder already sent?) before blindly retrying the side-effecting call. Longer term, classify tools by idempotency at design time — read-only lookups can always be retried freely, non-idempotent writes need either an idempotency key, a check-before-retry step, or explicit human confirmation before a retry fires.

**Situation:** You're asked whether your team should migrate an existing set of bespoke, framework-specific tool integrations to MCP servers now, given that the MCP spec has changed significantly within the past year (new stateless protocol core, deprecated primitives, SDKs bumped to new major versions). What would you do and why?

Model answer: Don't let "the spec is still moving" be a reason to avoid MCP altogether — a fast-moving but increasingly multi-vendor-backed standard is a different risk profile than a single company's proprietary format, and the direction of travel (OpenAI, Google, and Microsoft all shipping MCP support) suggests it's the safer long-term bet, not a risky one. Do treat it as a reason to be deliberate about timing and scope: start with the tool/data source most likely to be reused across multiple consumers (the strongest case for MCP in the first place), pin to the current stable SDK major version, and budget real time for the migration guide rather than assuming a drop-in swap, since a jump between major SDK versions (as with the recent v1-to-v2 rework) is typically a breaking change, not a patch. Keep the bespoke integrations that are genuinely single-consumer as they are — migrating those buys standardization with no reuse benefit to offset the migration cost.

**Situation:** Leadership wants a plain-language answer to "what's the actual difference between function calling and MCP, and are we choosing between them?" before approving budget for an MCP rollout. What would you do and why?

Model answer: Clarify that this isn't an either/or choice — function calling is the model capability (the LLM can emit a structured request to do something instead of just text), and MCP is a standard way to publish and discover a menu of those somethings (tools, plus data resources and prompt templates) so many different applications can share the same integration instead of each writing its own. Concretely: when Claude or GPT calls a tool exposed by an MCP server, that's still ordinary function calling happening under the hood — the host just got the tool's schema from an MCP server instead of from a hardcoded list in the app's own code. The budget question, correctly framed, isn't "function calling vs. MCP," it's "keep writing one bespoke integration per tool per application, or invest once in a standardized interface that pays off as soon as more than one application needs the same tool or data source" — and that payoff is proportional to how much reuse across teams/agents is actually expected.
